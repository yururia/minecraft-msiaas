> **改訂履歴**
> v1.0 → v2.0：認証方式の明確化、不在検知仕様の数値化、フォールバック方針の追加、MODライセンス対応方針の追加、料金モデルの追加、データ保持ポリシーの追加、各フェーズの完了定義（DoD）の追加、不正利用対策の追加、非機能要件の拡充

## 1. プロジェクト概要

### 1.1. プロジェクト名称

Minecraft MSIaaS (Minecraft Server Infrastructure as a Service)
※仮称：ワンクリックMODサーバー構築プラットフォーム

### 1.2. コンセプト

「技術でマイクラを自由にする。」
複雑なMODの依存関係、サーバー/クライアントの仕分け、インフラ構築、セキュリティ設定をすべて自動化し、ユーザーが「遊びたいMODを選ぶだけ」で最高のマルチプレイ環境を手に入れられるサービスを提供する。

### 1.3. ターゲットユーザー

- MODで遊びたいが、サーバー構築やMOD導入の知識がない初心者。
- ポート開放ができない、またはセキュリティ上の懸念でIPアドレスを公開したくないユーザー。
- 既存のレンタルサーバーでは性能に不満がある、または高額だと感じている層。

## 2. 機能要件

### 2.1. MOD解析・最適化エンジン

- **MOD選定ロジック**: 複数のMODから共通の対応バージョン（1.20.1等）とローダー（Forge/Fabric）を自動抽出。
- **依存関係解決**: 選択したMODに必要な「前提MOD」を自動でリストに追加。バージョン付き依存関係（例：MOD B v2.0以上が必要）を解決できること。
- **軽量化パック自動注入**: すべての構成に対し、描画・メモリ・計算負荷を最適化する「軽量化MODパッケージ」を自動的に付与。軽量化パックに含めるMODは別途管理台帳で定義し、マイクラバージョンごとにメンテナンスする。

### 2.2. サーバー・クライアント完全分離配信

- **自動仕分け機能**: 1つの構成リストを「サーバー用（システム側）」と「クライアント用（ユーザーPC用）」に自動分割。
- **ZIP解析インポート**: ユーザーが持っているMODパックのZIPファイルをドラッグ＆ドロップで読み込み、サーバー向けに再構築して取り込む。インポートされたプリセットは出所（`zip_import`）を記録し、手動作成のものと区別する。

### 2.3. インフラ自動プロビジョニング

- **自動構築**: Oracle Cloud（優先）またはAWS EC2のAPIを叩き、高性能な仮想マシンを**プロビジョニング開始から接続可能まで10分以内**にセットアップする。

- **自動終了ロジック**:
  - サーバーへの接続プレイヤーが0人になった時点を検知し、タイムスタンプを記録する。
  - プレイヤー不在が**15分継続**した場合、接続中のプレイヤー全員へ「5分後にサーバーが停止します」と警告を送信する。
  - 警告から**5分後**（合計20分）も不在であれば、ワールドデータをR2へバックアップした上でサーバーを停止・インスタンスを破棄する。
  - 停止処理中に新たなプレイヤーが接続した場合は停止をキャンセルし、タイマーをリセットする。

- **クラウドフォールバック方針**:
  - 優先プロバイダー：Oracle Cloud (ARM Ampere)
  - Oracleのプロビジョニング（APIリクエストから3分以内に応答がない、または明示的なエラーが返った場合）は失敗とみなし、自動的にAWS EC2でリトライする。
  - 両方失敗した場合はユーザーに「現在サーバーを起動できません。しばらくしてから再試行してください。」と表示し、エラー内容をログに記録する。
  - フォールバックが発生した場合、管理者へSlackまたはメールで通知する。

- **クラウド抽象化レイヤーの導入**:
  - AWSやOracle Cloudなど、将来的なプロバイダー追加や変更を容易にするため、インフラ操作を抽象化する共通インターフェースを実装する。
  - クラウド固有のAPI操作（SDK）をコアロジックから切り離し、ビジネスロジック（MOD構成やユーザー管理）が特定のクラウド仕様に依存しない設計とする。

### 2.4. 専用クライアントソフト (Tauriアプリ)

- **ワンクリック同期**: Webサイトで確定した構成を、ユーザーのPC上のマイクラ環境へ自動反映（MOD/Configの配置）。
- **P2Pセキュア接続**: Cloudflare Tunnelを活用し、ポート開放不要でサーバーへ暗号化接続を行う。

### 2.5. 仮想テスト＆AIデバッグ

- **起動シミュレーター**: 実際のサーバーを建てる前に、仮想環境で起動テストを実施。
  - 具体的には、選択したMOD構成に対してCloudflare Workers上で依存関係の整合性チェック・既知の競合パターンとの照合を行う。Java実行環境は含まない。
- **AIログ翻訳**: クラッシュ時に、専門的なログをAIが解析し、初心者にもわかる「日本語の解決策」を提示。
  - 解析結果（AI要約・使用したMOD構成・マイクラバージョン）はDBに保存し、類似クラッシュの再発防止に活用する。
  - AIの誤った解決策を提示するリスクがあるため、回答の末尾に「この解析は参考情報です。解決しない場合はコミュニティフォーラムをご利用ください。」と注記を付与する。

### 2.6. リソース割り当てポリシー

- **動的メモリ割り当てロジック**: MOD解析エンジンが算出した「想定負荷」に基づき、インスタンス作成時にJVM引数およびメモリ割り当て量を自動決定する。最小構成（バニラ/軽量MOD）では4GB、大規模構成では8GB〜16GBを基準値として割り当てる。
- **ストレージ・クォータ管理**: 1サーバーあたりのディスク容量に上限（20GB）を設定し、Cloudflare D1で利用状況を管理する。ワールドデータはセッション終了ごとに圧縮され、Cloudflare R2へバックアップとして転送・同期される。
- **リソースプロファイルの階層化**: Oracle Cloud (ARM Ampere) のリソースを、ユーザーの選択したMOD構成の「重さ」に応じて以下のプロファイルから自動選択してプロビジョニングする。

  | プロファイル | OCPU | RAM | 対象 |
  |---|---|---|---|
  | Standard | 2 OCPU | 12GB | 一般的なMOD構成 |
  | Performance | 4 OCPU | 24GB | 大規模MODパック |

### 2.7. MODライセンス・著作権対応方針

**本サービスはMODファイルそのものをホストまたは再配布しない。** 以下の方針に従って運用する。

- **Modrinthのオープンライセンスに限定（MVP）**: MVP段階では、再配布が明示的に許可されているModrinthのMODのみをサポートする。CurseForgeのMODはライセンス条件が複雑なため、MVP段階では対象外とする。
- **ダウンロードURLの中継方式**: MODファイルはユーザーのサーバーインスタンスがModrinthのCDNから直接ダウンロードする。当サービスはファイルを保持せず、ダウンロードURLと手順のみを提供する。
- **ライセンス情報の表示**: ユーザーがMODを選択する画面では、各MODのライセンス種別（MIT/LGPLなど）を表示する。
- **CurseForge対応（第2期以降）**: 第2期以降でCurseForge APIを利用する場合は、CurseForgeのAPI利用規約を精査した上で対応可否を判断する。

## 3. 認証・アカウント管理

### 3.1. 認証方式

MVP段階では **Cloudflare Access（Zero Trust）** を採用する。

- CloudflareダッシュボードでGitHub/Googleなどのソーシャルログインを設定し、認証済みユーザーのみがAPIへアクセスできるよう保護する。
- 認証後に発行されるJWT（Cloudflare Accessが自動付与）をバックエンドWorkers側で検証し、ユーザーIDを抽出してDBの`users.external_id`と紐付ける。
- 第2期以降でユーザー管理の高度化（プロフィール編集・パスワードリセット等）が必要になった場合はClerkへの移行を検討する。

### 3.2. MinecraftアカウントID

- ユーザー登録時またはサーバー初回起動時に、MinecraftアカウントのUUID（`minecraft_uuid`）の入力を求める。
- このUUIDはサーバーのホワイトリスト設定およびEULA遵守確認に使用する。入力は任意とするが、未入力の場合はサーバーを起動できない。

## 4. 料金モデル

MVP段階では以下の2プランを設定する。詳細な価格は別途決定する。

| プラン | 制限 | 備考 |
|---|---|---|
| Free | Standardプロファイルのみ / 月○時間まで | Oracle Cloud無料枠の範囲内で提供 |
| Pro | Performanceプロファイル利用可 / 月○時間まで | 課金はStripe経由（第2期以降） |

- **コスト超過時の対応**: Oracle Cloud無料枠を超えた分はサービス側が負担する（MVP段階）。超過が常態化した場合はProプランへの誘導またはFreeプランの制限強化を検討する。
- **Stripeとの連携**: MVP段階ではStripe連携を実装しない。DBの`plan`カラムを手動更新して運用し、第2期で課金フローを実装する。

## 5. データ管理・保持ポリシー

| データ種別 | 保存先 | 保持期間 | 削除タイミング |
|---|---|---|---|
| ワールドデータ | Cloudflare R2 | セッション終了から30日間 | 30日経過後に自動削除 |
| クラッシュログ（生） | Cloudflare R2 | 90日間 | 90日経過後に自動削除 |
| AI解析結果 | Cloudflare D1 | 無期限 | ユーザー退会時に削除 |
| ユーザーアカウント情報 | Cloudflare D1 | 退会まで | 退会リクエストから30日以内に削除 |
| 操作ログ | Cloudflare R2（Logpush） | 180日間 | 180日経過後に自動削除 |

- **ユーザーの退会処理**: ユーザーが退会を申請した場合、30日間のクーリングオフ期間を設け、その後すべての個人情報を削除する。ワールドデータは退会申請時に即時削除する。
- **GDPRへの対応**: 現段階では日本国内ユーザーを主な対象とするが、EU圏ユーザーが生じた場合を考慮し、「データのエクスポート」機能を第2期以降で検討する。

## 6. 不正利用対策

- **レートリミット**: 1ユーザーあたりのサーバー起動リクエストは1時間に3回まで。Cloudflare Workers側で制御する。
- **同時サーバー制限**: 1ユーザーにつき同時に起動できるサーバーは1台まで（DBの一意制約で保証）。
- **スパム登録対策**: Cloudflare Turnstile（ボット対策）をサインアップフローに組み込む。
- **ストレージ上限**: 1サーバーあたり20GBの上限を設け、超過した場合は起動を拒否しユーザーへ通知する。
- **不審なMODアップロードの検知**: ZIPインポート時にファイルサイズ上限（100MB）を設け、上限超過のZIPは受け付けない。

## 7. 非機能要件

### 7.1. セキュリティ

- **IPアドレスの秘匿**: サーバーのグローバルIPを公開せず、トンネル経由の通信のみを許可。
- **認証情報の保護**: クラウド操作用のAPIキーはバックエンド（Cloudflare Workers）内で秘匿管理。
- **Cloudflare TunnelのID管理**: セッション終了時にTunnel IDを使ってトンネルをAPIから確実に破棄する。URLのみでは削除操作ができないため必須。

### 7.2. パフォーマンス

- **プロビジョニング時間**: サーバー起動リクエストから接続可能まで10分以内（目標値）。
- **エッジ処理**: MODの検索や解析は、ユーザーに近いCloudflare Workersのエッジネットワークで高速実行。
- **配信最適化**: MODファイルはR2から最適な経路で配信。

### 7.3. 可用性

- Cloudflare Workers / D1 / R2 はCloudflareのSLAに依存する（99.9%以上）。
- Oracle Cloud / AWSのインスタンス起動失敗時は自動フォールバックにより復旧を試みる（2.3節参照）。

### 7.4. 拡張性

- **モジュール化設計**: 新しいマイクラバージョンや新しいクラウドプロバイダー（Google Cloud等）へ容易に対応できる設計。

### 7.5. 監視・アラート

- Cloudflare Logpushで操作ログをR2へ転送し、異常検知の基盤とする。
- サーバー起動失敗・フォールバック発生・ストレージ上限接近（80%超）は管理者へ通知する。
- 通知チャネルは第1期ではSlack Webhookとする。

## 9. 開発フェーズ（ロードマップ）

### 第1期：MVP（実証モデル）の構築

**目標**: 特定の1バージョン（1.20.1/Forge）に絞り、WebからOracleサーバーが起動し、プレイヤーが接続できるまでの基本フローを完成させる。

**完了定義（DoD）**:
- ユーザーがサインアップ〜MOD選択〜サーバー起動まで一連の操作を完了できること。
- プロビジョニングが10分以内に完了すること（成功率80%以上）。
- **第1期の接続方式**: Tauriアプリは未リリースのため、サーバーのIPアドレスを管理者がユーザーへ直接共有する方式とする（開発者向けβのみ）。セキュリティリスクを承知の上で一時的な措置として採用し、第3期で完全に廃止する。
- 自動終了ロジック（20分不在でシャットダウン）が動作すること。
- Oracle→AWSへのフォールバックが動作すること。

### 第2期：インテリジェント化

**目標**: MOD解析の精度を上げ、サービスの差別化機能を完成させる。

**完了定義（DoD）**:
- ZIP解析インポートが主要なMODパック形式（CurseForge形式・Modrinth形式）で動作すること。
- サーバー/クライアントの自動仕分けが90%以上のMODで正確に動作すること。
- 軽量化パックが1.18〜1.21の全バージョンに対応すること。

### 第3期：ユーザー体験の完成

**目標**: 一般ユーザーが技術知識ゼロで使えるレベルのUXを実現する。

**完了定義（DoD）**:
- Tauri製クライアントアプリがWindows/macOSでリリースされること。
- Cloudflare Tunnelによる接続が動作し、第1期の直接IP接続を廃止すること。
- ユーザーがアプリをインストールしてサーバーに接続するまで10分以内で完了できること。

### 第4期：高度な保守・運用

**目標**: コスト最適化と運用の自動化を完成させる。

**完了定義（DoD）**:
- AIログ解析機能がリリースされ、主要なクラッシュパターン（上位10件）に対して適切な解決策を提示できること。
- オートスケーリングと自動シャットダウンにより、無人稼働コストをゼロに近づけること。

## 11. 開発規約（技術構成の決定事項）

### 11.1. モノレポ構成とビルドパイプライン

ビルドツールは **Turborepo**（`turbo.json`）を使用する。パイプラインは以下の順序で実行される。

```
packages/* のビルド → apps/* のビルド → lint / test → deploy
```

`dependsOn: ["^build"]` により、各パッケージは依存先のビルドが完了してから自分のビルドを開始する。

### 11.2. 依存方向のルール（循環依存の防止）

**`packages/` は `apps/` に依存してはならない。** 依存の方向は必ず一方向のみ。

```
packages/shared
packages/cloud-provider   →   apps/api
packages/mod-db-tools     →   apps/provisioner
                          →   apps/web  など
```

このルールはコードレビューだけでなく、**dependency-cruiser**（`.dependency-cruiser.cjs`）によって機械的に検証する。`lint:deps` スクリプトをCIに組み込み、違反があればビルドを失敗させる。

```bash
# ローカルでの検証
pnpm lint:deps
```

違反例（エラーになる）:
- `packages/cloud-provider` が `apps/api` の型をインポートする
- `packages/shared` が `apps/web` のコンポーネントを参照する

### 11.3. Cloudflare Queue バインディングの管理ルール

`api/`（Producer）と `provisioner/`（Consumer）はQueue名で接続されている。**片方だけ変更するとQueue接続が切れる**ため、以下をルールとする。

| 設定ファイル | 役割 | Queue名 |
|---|---|---|
| `apps/api/wrangler.toml` | Producer（ジョブ投入） | `msiaas-provisioning-jobs` |
| `apps/provisioner/wrangler.toml` | Consumer（ジョブ処理） | `msiaas-provisioning-jobs`（同一名） |

**変更時の手順**:
1. 両ファイルを同一PRで変更する（片方だけのPRはマージ禁止）
2. Queue名を変更する場合は、新旧両方のQueueを一時期並走させてから旧Queueを削除する
3. PRレビュー時は両ファイルのQueue名が一致しているか確認する

### 11.4. MODキャッシュの定期更新（Cron）

MVP段階では `apps/api/` に Cloudflare Workers の `scheduled()` ハンドラを追加し、Modrinthから最新のMOD情報を取得してD1に書き込む処理を実行する。

- 実行タイミング：毎日 UTC 03:00（日本時間 12:00）
- 設定場所：`apps/api/wrangler.toml` の `[triggers] crons`
- 実装場所：`apps/api/src/scheduled.ts`

第2期以降でキャッシュ更新の処理量が増加した場合は、専用の `apps/cron/` Workerへ切り出すことを検討する。

### 11.5. シークレット管理のルール

APIキー等のシークレットは **`wrangler secret put`** コマンドで管理し、`wrangler.toml` や `.env` ファイルに平文で記載しない。

```bash
# 例：Oracle APIキーの登録
wrangler secret put ORACLE_API_KEY --env production
```

`wrangler.toml` の `[vars]` セクションには公開可能な環境変数のみ記載する。必要なシークレットの一覧は各 `wrangler.toml` のコメントに記載し、新規メンバーがセットアップできるようにする。
